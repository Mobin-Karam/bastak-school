# Database migration and rollback compatibility plan

Prepared **before persistence implementation**, 2026-10-12, baseline `fce04c6e6e2d8110a4217233eece973d521c9a4d`. Scope is SQLite/TypeORM hardening and an evidence-based audit, not a PostgreSQL cutover or production database operation.

## Safety boundary and ordering

1. Inventory all entity metadata and the schema produced by the complete historical migration chain in a newly created disposable database. Do not open the application's configured database path. Keep `synchronize: false` for new integration tests and measurements.
2. Generate synthetic schools/students/classes/attendance/rooms. Measure actual query patterns and TypeORM hydration before altering their implementation or indexes; collect EXPLAIN QUERY PLAN and warm-cache latency samples. Production workload performance remains UNKNOWN.
3. Back up the disposable populated database with the same SQLite online-backup mechanism used by deployment. Restore into another disposable file, check `integrity_check`, `foreign_key_check`, schema objects and every table's logical content before applying new migrations.
4. Add versioned, additive index/constraint migrations. Candidate constraints are attendance `(sessionId,studentId)` and one current dorm placement per student, based on explicit service semantics. Inspect actual migrated constraints first. Any conflicting historical records cause preflight failure **without deleting, merging or updating records**. Do not renumber/replay historical migrations or hide already-applied damage. If the populated pending NightAttendance regression proves destructive, remove its unnecessary SQLite varchar-length rebuild while retaining its historical ID; this protects pending upgrades without rewriting deployed history. Restore missing read indexes in the new versioned migration.
5. Make dorm replacement/movement atomic and serialize its writes using existing SQLite writer admission. Replace roster hydration for room counts only after baseline measurement. Add integration tests for rollback, contention, uniqueness, school ownership and backup restoration.
6. Strengthen tenant/resource checks that currently re-use an unrelated membership. Use server-resolved work-context organization IDs and active organization/membership state; preserve deliberate platform-admin semantics. Run the security matrix after authorization changes.
7. Verify fresh migrations, populated upgrades, unchanged rows/custom schema objects, constraint failures and index-only rollback on disposable files. Run relevant project and release gates. Production rollout is a separate operator action with a verified retained backup.

## Candidate changes and compatibility

| Change | Record compatibility | Rollback and risk |
| --- | --- | --- |
| Attendance unique index | No rewrites; refuse existing duplicate pairs. Existing occurrence and request-receipt uniqueness stays. Different sessions for the same student remain valid. | Application rollback may retain stronger schema. Dropping only the new index loses that database guarantee; drain writers before doing so. No attendance facts are removed. |
| Presence current-task unique index | Later inventory found a OneToOne/migration mismatch. `ActivityService` only accepts tasks owned by the presence student's plan, so two students cannot legitimately share that task pointer. Reject duplicate non-null pointers without changing them; multiple NULL values remain valid. | Index-only rollback; task/presence facts remain. Historical conflicting ownership must be resolved explicitly before rollout. |
| Current dorm-placement unique index | One student has one primary school; DormitoryService explicitly moves students from their prior current room. Preflight reports conflicting placements by aggregate count, without exposing student data. | Leave stronger uniqueness in place with code rollback when possible. Index removal is non-data-destructive but permits duplicates; retain preflight backup and stop writes. Do not infer a historic-placement cleanup policy. |
| Measured read indexes | Add only when plans/measurements show benefit for real predicates/orderings. Existing indexes are preserved, including redundant historical ones. | Index-only down migration, no table rebuild. Disk/write amplification and lock time require rollout measurement. |
| Atomic placement commands/count projections | Same HTTP shapes; delete-and-replace retains its existing API semantics inside a transaction. Do not change primary ownership, capacity or student lifecycle implicitly. | Revert code through a normal fix PR; do not reset the database. Old placement writers must tolerate the new uniqueness constraint or remain disabled. |
| Tenant guard hardening | Valid same-school/platform workflows remain available; cross-school membership alone no longer conveys current-role authority. | Security regression coverage before merge. Do not roll back by removing checks to satisfy a client. |

Legacy manual attendance session creation has no request identity; two distinct sessions on the same date may be intentional. Do **not** introduce `(context,date)` uniqueness or collapse historical sessions. Scheduled occurrences and retried marks have explicit occurrence/request keys; verify their concurrency behavior and database guarantees instead.

## Operator rollout and rollback

Do not run production reset, destructive seed, automatic schema synchronization or a mass `migration:revert`. SQLite remains one API replica with a persistent disk. Before deployment: stop/drain writes where needed, create a consistent online backup, retain it off-host, restore a copy in isolation, check integrity/FKs, compare row counts and deterministic logical content, rehearse the pending migration chain and test application reads. A backup that has only been copied is not verified recovery.

Run constraint preflight on the authorized isolated restore. If duplicates, orphan references or ownership ambiguity exist, stop and obtain an explicit remediation decision; preserve every conflicting record. Do not auto-select a winner. Budget extra disk and downtime for index construction. Current `migrationsRun: true` applies pending migrations at application startup; additive migrations can still abort startup on conflicting legacy data, so rehearsal is mandatory. No production command is executed by this audit.

New rollback removes only objects introduced by the new migration. Existing historical forward-only migrations cannot be undone safely by index rollback. The latest integrity migration and timetable/lifecycle migrations explicitly disallow schema reversal. The old NightAttendance down path filters records and is not an approved recovery procedure; the safety correction rejects that rollback rather than deleting night/pool facts. Restoring a snapshot loses subsequent writes: freeze writers and define a replay/reconciliation point before recovery. Preserve migrations table and custom indexes/triggers.

## SQLite-to-PostgreSQL strategy (future, not executed)

1. Define operational triggers for the move: measured write contention, growth, required high availability or multiple API replicas. Establish downtime/RPO/RTO requirements before choosing offline cutover versus CDC.
2. Produce a table-by-table ownership/type/constraint ledger from actual migrated SQLite. Resolve orphan/tenant mismatches and duplicate conflicts through reviewed migrations first, preserving history. Global users and student national-code uniqueness are existing semantics; do not silently convert them to per-school identity.
3. Add a separately tested PostgreSQL TypeORM adapter with explicit types and migrations. Translate UUID/text conventions, booleans, datetime/time-zone semantics, JSON/simple-array fields, autoincrement migration bookkeeping, partial indexes, CHECKs, trigger-based scope rules, collations, NULL uniqueness and cascade/restrict behaviors. SQLite pragmas, `INSERT OR IGNORE`, `changes()`, `datetime('now')`, VACUUM INTO and positional `?` raw SQL need adapter-specific implementations; connection-string replacement is insufficient.
4. Use a disposable PostgreSQL integration profile running the same public contract, security, transaction, attendance idempotency, placement and migration tests. Prove row-level locking/retry behavior under separate concurrent connections; the SQLite in-process queue is not a PostgreSQL concurrency strategy. Decide explicit tenant columns/composite references or RLS; RLS must supplement resource policy and require scoped connection context.
5. Rehearse snapshot export/import preserving IDs, statuses, timestamps, FK order, audit history and migration provenance. Compare deterministic per-table digests/counts, foreign references, query results, permission decisions and measured plans. Do not copy a SQLite migrations table as proof PostgreSQL DDL ran.
6. Freeze writes, take/verify final backup, import/validate, switch a controlled canary and then clients. Keep SQLite read-only as the recovery boundary. Before PostgreSQL writes begin, rollback can switch back; afterwards, rollback requires tested reverse export/replay or restoring to an explicitly accepted recovery point. No unsupported dual-write period.

## Evidence to complete

The implementation audit report will record schema inventory, confirmed versus potential issues, synthetic baseline/after measurements, restore verification, integration checks and unresolved production facts. This plan permits additive local development and disposable tests only; it does not authorize production database modification or premature engine migration.
