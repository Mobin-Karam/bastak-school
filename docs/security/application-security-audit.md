# Application security audit

Reviewed 2026-10-13 from develop `39f339500bb8daeac0d5c2cb7dc4402c41ca5fe0`. This audit uses source, fresh migrations, disposable HTTP integration tests and read-only deployment checks. No production credentials, student rows or account assignments are included. The absent Graphify graph required source-level discovery. [Permission matrix](permission-matrix.md) covers all 16 migrated roles and 181 permissions; [exact grants](permission-baseline.json) are reproducible migration defaults, not a dump of production assignments.

## Threat model and current enforcement

The live application is NestJS **Fastify**, TypeORM/better-sqlite3, React/Vite Admin used by both staff and students, CMB platform packages and a single-server Docker/Nginx deployment. `apps/student` is absent; the retained `student-core` package is not a second deployed frontend. `apps/api/src/app.module.ts` and `platform/cmb-platform.module.ts` determine mounted modules. GuardianModule transitively mounts ExamsModule; legacy modules cannot be assumed dormant merely because they are not direct AppModule imports. StudentDocumentsModule is explicitly dormant.

Threats considered: anonymous requests, authenticated students/guardians guessing other records, staff crossing school or selected role boundaries, replay/concurrency, credential exposure through ORM relations, malicious input/uploads, compromised deployment credentials and accidental logging of personal data. Platform owner is intentionally highly privileged. Explicit chat conversation membership is a separate resource authority; whether losing school membership must revoke historical conversations remains a policy decision.

`AuthSessionGuard` resolves cookie-backed sessions and re-enriches role/capability context against active memberships. RolesGuard and CapabilitiesGuard enforce metadata; CsrfGuard covers authenticated mutations. Services still enforce object ownership. `CurrentUser` now rejects missing identity consistently, including endpoints without capability metadata. A hidden frontend button never grants or denies backend authority. Forged role/organization headers fail in AuthorizationService. `AuthorizationService.canAccessStudent`, SchoolAccessService and feature-specific class/delegate/conversation policies provide resource boundaries.

Passwords use bcrypt: new onboarding/admin accounts and password changes use cost 12; retained legacy helper writes use cost 10. Access, refresh and CSRF credentials use cryptographic random bytes; access/refresh values are SHA-256 hashed in SQLite. Timing-safe comparisons validate CSRF. Default access lifetime is 15 minutes and refresh lifetime 30 days; successful refresh extends the refresh lifetime, so there is no separate absolute session lifetime. Disabled accounts and unusable work contexts fail authentication. Password changes revoke other sessions; staff reset paths revoke sessions. There is no mounted email/SMS forgotten-password recovery flow: student reset is a staff-authorized operation. Academic `recovery_requests` are not password recovery.

Cookies are HttpOnly and production Secure by default; SameSite is configurable (LAN explicitly lax, generic production default none). CORS is an explicit credentialed origin allowlist. The audit did not reveal or alter actual production secret values. TRUST_PROXY is enabled in production Compose; API ingress must remain behind the controlled proxy. Login/check-phone throttling is SQLite-backed and signup has a separate persistent budget. Refresh/logout do not add new security libraries. Global DTO validation rejects extra fields only when the route uses a concrete decorated DTO; interfaces/`any` need service validation.

## Safe release and rollback compatibility

This security change adds no database migration, new middleware library or dependency upgrade. `select:false` is query metadata only. No account/session/relationship reset, seed, production role change or file deletion is required. Only sessions deliberately refreshed/logged out and unauthorized requests change behavior. The integrated release also includes previously reviewed develop persistence changes: check its complete migration diff rather than assuming the entire release is schema-free.

Retain current images before building/recreating; verify snapshot restoration and rehearse pending candidate migrations on a copy before production startup. Never revert/drop indexes or triggers automatically or restore an older database over new student records. Reverting application code can reintroduce the defects above. Follow [reliability runbook](../operations/reliability-runbook.md) and existing [database compatibility plan](../architecture/database-migration-plan.md). Production release status and exact image IDs are recorded separately from audit findings.
